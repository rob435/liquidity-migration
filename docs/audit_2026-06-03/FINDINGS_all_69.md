### [HIGH] continuous-2 — Same-hour cover-then-re-entry produces a duplicate trade_id (and duplicate Bybit orderLinkId): the closed trade is silently dropped from the ledger / the re-entry order is rejected
- **subsystem/category:** continuous / data-integrity  | **fix_safe:** False  | **round:** r1b
- **loc:** `liquidity_migration/continuous_demo.py:884,1110-1116 ; storage.py:139,422-434 ; order_link_id.py:28-31`
- **evidence:** trade_id = f'{strategy_id}-{symbol}-{signal_ts_ms}' and signal_ts is the deciding-bar hour = cur_hour_ts-(1+delay)*MS_PER_HOUR (continuous_demo:1110-1116) — CONSTANT for the whole wall-clock hour. The only re-open guard is _recent_exit_cooldown_symbols (reentry_cooldown_minutes=30), which does NOT cover the full 60-min hour: enter H:00, left_decile-cover H:05, cooldown lifts H:35, re-enter H:40 (back in D9) → identical signal_ts → identical trade_id. I reproduced the collision arithmetically. storage._write_part dedups continuous_fade_demo_trades on trade_id (DATASET_KEYS line 139) keeping max updated_at_ms (lines 432-434) → the OPEN re-entry row (newer) wins and the CLOSED trade row is permanently dropped from the parquet, erasing its realized PnL/exit record. Independently, _order_link_id (lm-en-c-{base}-{base36(signal_ts//1000)}) is ALSO identical for the re-entry, and Bybit rejects duplicate orderLinkIds → the live place_order raises → status='failed' and the re-entry signal is silently missed.
- **impact:** CORRUPTS THE LEDGER + LOSES A SIGNAL: a realized continuous trade vanishes from the trade ledger (broken accounting / reconciliation gap / understated trade count), and/or the re-entry order is rejected by Bybit so the sleeve silently skips a valid D9 entry. Affects both d1 (+1h) and legacy d0 entry modes.
- **proposed_fix:** Make the ledger key collision-proof: build trade_id from a monotonic open instant (entry_ts_ms / now_ms) rather than the shared signal_ts (keep signal_ts as a separate column), OR add a per-open sequence suffix; and add a per-account-unique nonce/sequence to the entry orderLinkId so a same-hour re-entry cannot reuse a prior link. Add a regression test: same-symbol cover then re-enter within the same deciding-bar hour must produce two distinct trade_ids and two distinct orderLinkIds, and the closed row must survive a write/read round-trip.
- **verifier fix-notes:** The bug is real, but the proposed fix as written is NOT side-effect-free, because trade_id is contractually coupled to the orderLinkId.

ws_risk's rebuild-safe recovery (ws_risk.py:1461-1472, _build_adopted_trade) reconstructs trade_id = f"{strategy_id}-{symbol}-{signal_ts_ms}" by decoding the Bybit-retained orderLinkId back to signal_ts via decode_entry_order_link_id (order_link_id.py:51-89, which returns only (sleeve, signal_ts_ms)). The deterministic trade_id MUST stay derivable from (strategy_id, symbol, decode(orderLinkId)). 

The proposed half "build trade_id from entry_ts_ms/now_ms instead of signal_ts" therefore BREAKS that reconstruction: after a VPS rebuild the local ledger is gone, ws_risk re-derives trade_id from the orderLinkId, and an entry-instant-based trade_id is not encoded anywhere in the orderLinkId -> the recovered trade_id no longer matches the original -> the position falls back to the lossy adopted-* path, reintroducing the very orphan-mismatch class this code exists to prevent (and not just for continuous -- the reconstruction path is shared by short/long too).

The orderLinkId-nonce half is also constrained: Bybit caps orderLinkId at 36 chars (order_link_id.py:31, [:36]) and any added per-open sequence/nonce must be parsed back out by decode_entry_order_link_id AND by ws_risk's trade_id reconstruction, or routing/recovery breaks.

A correct, side-effect-free fix must keep trade_id derivable from the (extended) orderLinkId -- e.g., add a per-open sequence suffix to BOTH the trade_id AND the orderLinkId (within the 36-char cap, base truncated first as _split_order_link_id already does) and teach decode_entry_order_link_id + the ws_risk reconstruction to recover that suffix. A simpler alternative that avoids the encoding contract entirely: extend the re-entry suppression to cover the full signal_ts period (i.e., block re-opening a symbol whose last entry shares the current signal_ts, or set the effective cooldown >= 60 min / >= the signal_ts granularity) so a collision can never form in the first place. The auditor's requested regression test (cover-then-re-enter within the same deciding-bar hour -> two distinct trade_ids AND orderLinkIds, closed row survives a write/read round-trip) is the right gate, but it must also assert the VPS-rebuild reconstruction (decode orderLinkId -> trade_id) still resolves for both legs.

### [HIGH] data-assembly-3 — residual_momentum is joined on a start-of-day key while the engine feature panel carries an end-of-day ts_ms — possible whole-signal day shift
- **subsystem/category:** data-assembly / methodology  | **fix_safe:** False  | **round:** r1c
- **loc:** `liquidity_migration/volume_events.py:329-343`
- **evidence:** _attach_residual_momentum builds `_rm_day = (ts_ms // ms_per_day) * ms_per_day` on BOTH the signal table and the feature panel (lines 334, 340) and left-joins on it. But the feature panel's `ts_ms` is the END-of-trading-day stamp (`day_start_ms + MS_PER_DAY`, volume_events_features.py:568) — flooring it with `// ms_per_day * ms_per_day` yields the day AFTER the trading day. If scripts/precompute_residual_momentum.py writes residual rows stamped at the trailing-residual day's own ts (start/close of day D) rather than D+1, the two `_rm_day` values describe different calendar days and the gate either drops the candidate (is_not_null filter) or attaches residual_momentum[D] to the wrong signal day. The precompute docstring says the live join 'floors now to TODAY's day_ts and exact-matches', implying a start-of-day key, which is NOT the engine panel's end-of-day key.
- **impact:** alpha: a one-day misalignment between the residual-momentum selection gate and the volume-event panel would either silently empty the gated sleeve (no trades) or shift the selection signal a full day off the decision day — a correctness bug in the residual-momentum-gated profile that backtest-vs-live reconciliation may not catch if both sides share the same off-by-one.
- **proposed_fix:** Make the join key explicit and identical in semantics on both sides: derive the trading day from the panel via trading_day_expr('ts_ms') (date of ts_ms-1ms) and from the residual table via its actual completion-day convention, then join on a string date, not a raw modulo floor. Add a test that asserts, for a known (symbol, day), the residual_momentum value attached to the event row equals sum(residual_return[D-7..D-1]).
- **verifier fix-notes:** The proposed fix is DIRECTIONALLY CORRECT but NOT a safe drop-in as literally phrased — apply with care.

Root cause: the two sides use DIFFERENT day conventions, so any fix must use the RIGHT (asymmetric) key on each side:
- Engine panel: trading day = date(ts_ms - 1ms) = trading_day_expr('ts_ms') (end-of-day stamp).
- Residual table: trading day = date(ts_ms) (start-of-day grid; its ts_ms already labels decision day D).

CORRECT FIX: join engine.trading_day_expr('ts_ms') == residual.date(ts_ms). Equivalently in the raw-modulo form: subtract MS_PER_DAY from the panel side before flooring (panel _rm_day = ((ts_ms - 1)//ms_per_day)*ms_per_day so day-D event maps to day_start(D)), leaving the residual side as-is.

PITFALL the verifier must flag: the finding's text says "derive the trading day from the panel via trading_day_expr AND from the residual table via its actual completion-day convention." That is right ONLY if the residual side is NOT also passed through trading_day_expr. Applying trading_day_expr to BOTH sides (the naive reading) shifts both by the same -1ms and PRESERVES the off-by-one — it would not fix anything. So the implementer must explicitly use trading_day_expr on the panel and plain date(ts_ms) on the residual table.

SIDE-EFFECT / non-no-op warning: this is a methodology correction, NOT a numerically-equivalent refactor. Fixing it WILL change which candidates survive the rmom gate and therefore changes the backtest output of every rmom-gated research cell (it currently silently selects the wrong, look-ahead day). Any prior age-rmom-ff6-combined results produced with the current code are tainted and must be re-run; a pre-registration receipt should accompany the re-run per AGENTS.md. It is safe for the live system (deployed/continuous paths don't use _attach_residual_momentum), so no live-trading risk from applying the fix.

REQUIRED REGRESSION TEST (the finding's suggestion is the right one): build a tiny klines + residual_momentum fixture for a known (symbol, D), run the engine join, and assert the residual_momentum attached to the event on trading day D equals the residual-table value for decision day D (i.e. sum(residual_return[D-7..D-1])), and explicitly that it does NOT equal day D+1's value. This locks the asymmetric key and would have caught the current bug.
